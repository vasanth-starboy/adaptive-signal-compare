Run the algorithm here (no Python needed)

Choose your raw probe CSV (columns: timestamp, probe_id, speed, approach_id, optional signal_id), edit the settings if you like, and press Run. Every graph on this page then fills in from the result. This is a simplified browser copy of the Python program: it skips the Wmin offset refinement and does not compute prediction error, demand accuracy or the scalability test, so use Python for final report numbers.

Dynamic comparison over time

Upload one or more results.csv files, one per algorithm; the file name becomes its label. Pick a metric and every algorithm is drawn window by window. For delay and travel time, the other published algorithms are drawn as dashed lines: your own fixed-time baseline reduced by each algorithm’s published improvement.

1. Average delay: improvement vs fixed-time (%)

Dalian values are computed from that paper’s Table 1 against its fixed-time control. Field values are agency-reported averages. Your value is the model estimate.

2. Average travel time: improvement vs fixed-time (%)

Dalian values use total network travel time. No comparable SCOOT travel-time average was found, so it is left out.

3. Arrival-on-green ratio (%)

No comparable published arrival-on-green figures were found, so this compares your adaptive offsets with your own fixed-time baseline (offsets all 0).

4. Throughput: gain vs fixed-time (%)

Only one published figure was found (ACDSS field report). Your throughput gain can’t be computed from probe data recorded under fixed-time control; enter one if you have it.

5. Arrival / travel-time prediction error (MAPE %)

Published value: mean travel-time MAPE at 5% probe penetration (speed-map reconstruction), a different method from yours. Lower is better.

6. Demand estimation accuracy (%)

Published values are best-case results (arrival-rate error 4.2%, volume error 0.9%) from a low-penetration connected-vehicle study.

7. Computation time per control update (ms, log scale)

Slower published methods: a genetic algorithm takes 40–55 s (plotted at 47.5 s) for one intersection, and MILP-MPC about 0.9 s for one intersection. The 6-intersection values are whole-network updates. The distributed DP figure is a median upper bound per intersection. All are on the authors’ hardware and solve somewhat different problems from yours.

8. Scalability: update time vs number of intersections (ms, log scale)

Your curve is from section 8(b) of your report. The far-right triangle is a published SDP offset optimizer that reports near-linear scaling and finishing 12,000 intersections within an hour, so it is an upper bound.
